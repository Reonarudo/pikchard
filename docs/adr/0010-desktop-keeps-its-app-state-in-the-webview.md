# Desktop keeps its app state in the webview, not in native files

Pikchard carries four pieces of state that are not the user's Documents: Recent, Drafts, the theme choice and the split-gutter ratio. The web build has nowhere to put them but the webview's own storage. The desktop build had a choice — reuse exactly that, or write native files through a Tauri store — and a desktop app that keeps its preferences inside a webview instead of the platform's config directory is unconventional enough to be worth recording.

We reuse the web storage. The `Platform` seam (ADR 0001, #1041) exists to abstract *file* access, because that is where the two Platforms genuinely diverge — pickers, handles, paths, scopes. Preferences and Drafts do not diverge: they are key-value state the app owns, and giving them a second backend would mean a second implementation, a second set of tests and a second set of failure modes for state that was never the user's to manage. The cost is real and we accept it: webview storage lives inside the app's data directory rather than somewhere a user can inspect, back up or hand-edit, and clearing the webview's data takes Recent and every Draft with it. That is survivable only because of what these things are — #1054 settled that a Draft is crash insurance, not session restore, and made that promise no stronger than the storage could keep (Safari's ITP evicts script-writable storage after seven days, so the web build cannot promise durability and the product therefore never does). Recent is a convenience list of at most ten entries, every one of which the user can recreate by opening the file again.

## Consequences

- The `Platform` interface gains no preferences method. Anything that reaches for one is either a Document operation in disguise or a sign this decision needs revisiting.
- `tauri-plugin-single-instance` becomes load-bearing rather than merely tidy, and is registered on **all three** OSes (#1057) — not just Windows and Linux, where a second "open with" spawns a genuine second process. Two instances of a macOS app share one data directory, so `open -n` would put two Pikchards on one set of Drafts. A storage decision that assumes a single writer has to enforce it.
- Reversing this is a migration, not a config edit: something must read the old keys out of the webview and write them to a file. That is the price, and it is known.
- Nothing here applies to the Documents themselves. Those never live in webview storage on desktop — they are files on disk, reached through the `Platform`, and the Draft is only ever a copy of one that has not been saved yet.

# The web build's Content Security Policy is defence-in-depth, not a control

ADR 0003 promised that the web build "ships with a strict Content Security Policy". Delivering one on GitHub Pages means a `<meta http-equiv>` tag, because Pages serves no custom response headers — and CSP Level 3 §3.3 makes `frame-ancestors`, `sandbox`, `report-uri`/`report-to` and report-only mode inert inside a meta element. The policy therefore cannot prevent framing and cannot report a violation, whatever we write in it. Within what it *can* express, the one contested directive is `style-src`: CodeMirror mounts its theme by injecting a `<style>` element, and pikchr's SVG output carries an inline `style='font-size:initial;'` attribute on its root, so a strict `style-src` would require both mounting the editor in a ShadowRoot — where `style-mod` switches to a constructed `CSSStyleSheet` that browsers do not currently gate — and stripping that attribute before every insert. The third option, a nonce via `EditorView.cspNonce`, is not available to a static site: with no server to vary it per request it would be a hard-coded constant, which is the appearance of a defence rather than one.

We took `style-src 'unsafe-inline'` and kept `script-src` strict at `'self' 'wasm-unsafe-eval'`. Under ADR 0003 there is no server, no accounts, no cookies, no third-party script and no user-supplied HTML, so the CSP is not a control that any other decision leans on — it is a second line behind a codebase that has no first-line breach to cover. Buying a permanently more complicated editor component (#1085) to satisfy a directive whose threat it is not blocking is the wrong trade, and making that judgement explicit is the point of this record.

## Consequences

- The policy is injected at build time by a `transformIndexHtml` plugin that is present only when `TAURI_ENV_PLATFORM` is unset. It must never reach the desktop build: Tauri 2 with `security.csp: null` emits no policy of its own, so a shared meta tag would silently become the desktop app's only policy, block the IPC `fetch` into its `postMessage` fallback and break `asset:` URLs outright.
- **The desktop build reaches the opposite conclusion, and the reason is the whole point** (#1057). This record's argument is that the web build has no first-line breach to cover; the desktop build does, because its webview holds Tauri IPC and IPC reaches the filesystem. The one path from untrusted input to the DOM is the same on both — a Script from a downloaded file becomes pikchr's SVG output, injected into the Preview, since Markdown prose is never rendered to HTML (#1052) — but on the web it ends at a defaced tab and on the desktop it ends at arbitrary file read and write. So the desktop ships a real policy through `security.csp` in `tauri.conf.json`: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; connect-src 'self' ipc: http://ipc.localhost; font-src 'none'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; frame-src 'none'`. Reading the two policies side by side and concluding that one of them is a mistake would be the misreading this bullet exists to prevent.
- `style-src 'unsafe-inline'` is unchanged on desktop. It is the same CodeMirror constraint, and tightening it there would buy the ShadowRoot refactor this record already priced and declined.
- The desktop policy deliberately omits `asset:`. Pikchard reads files as text through the fs plugin and never loads one by URL, so `asset:` would be permission for a capability it does not use. If `convertFileSrc` is ever introduced, the policy must change with it — CSP3 §8.1 makes multiple policies intersect, so nothing else can loosen it back.
- `frame-ancestors 'none'` appears on desktop and not on web. That is not an inconsistency but the direct consequence of the meta-tag limitation above: the directive is inert in a meta element and live in a response header, so the desktop policy can express the one protection the web build had to concede.
- The dev server ships no policy at all. `@vitejs/plugin-react` injects an inline module preamble in development, so a dev policy would have to be a weaker, different policy — one that tests nothing. The cost is that violations surface only in the built app, so a Playwright check against `vite preview` asserts that no `securitypolicyviolation` event fires.
- **`tauri dev` ships no desktop policy either** (#1099). Tauri 2 applies `security.csp` (or `devCsp`) only as a response header from its own `tauri://` protocol. In dev on desktop, the webview loads `devUrl` straight from Vite, and only mobile proxies it through that protocol: `get_app_url` and `PROXY_DEV_SERVER = cfg!(all(dev, mobile))`, in `tauri` 2.11's `manager/mod.rs` and `manager/webview.rs`. Nothing sends the header, so the desktop policy is inert in dev for the same reason the web one is. This was read from the source rather than observed in devtools. Setting `devCsp` would change nothing. The mitigation is the same as the web's: a check on the built app. `e2e/desktop-csp.spec.ts` serves the desktop build under this policy, in Chromium and in WebKit (the engine of the macOS and Linux webviews), and item 2 of the [desktop release checklist](../desktop-release-checklist.md) looks at the real bundle.
- Tauri adds a nonce to `style-src` for every `<style>` element in the page, and a nonce makes browsers ignore `'unsafe-inline'`. So `dangerousDisableAssetCspModification: ["style-src"]` is set. Without it, one `<style>` added to `index.html` would silently strip CodeMirror's theme in the built desktop app only. `script-src` is still modified: Tauri hashes the inline theme script (#1022) into it, as the web plugin does.
- `img-src` carries `blob:` and `data:` because PNG export rasterises through `<img src="blob:…">` (#1021) and Vite inlines small assets as data URIs. Removing either breaks export rather than tightening security.
- `font-src 'none'` is a claim about the app, not a leftover: the shell loads no font files and uses system stacks only. If a web font is ever added, CSP failing loudly is the intended outcome.
- `script-src` also carries a `'sha256-…'` hash for each of `index.html`'s inline scripts, computed from the built page by the plugin that injects the policy (#1025). There is one: the theme is read before the first paint (#1022), and without its hash the policy would block it and the dark theme would flash white on every load. A hash allows exactly those bytes, so `script-src` stays free of `'unsafe-inline'`. Because the hash is recomputed from every build, editing the script cannot leave a stale one behind.
- The web build can be framed by any site and we accept it. There is nothing to clickjack — no account, no cookie, no destructive one-click action, no server state. A framebusting script would be the bundle's only inline script and would need its own hash in `script-src`, paying a real cost against no asset.
- Tightening `style-src` later is a refactor of the editor component, not a config edit. That is the price of this decision and it is known.

# Commit the upstream Script corpus; do not rebuild it at test time

Both the renderer and the grammar are tested against the Scripts in the pinned pikchr tarball: `pikchr-wasm` renders them and compares against goldens, `lang-pikchr` parses them and requires zero error nodes. The tarball is already vendored (ADR 0005), so the corpus can either be unpacked from it on every run or extracted once and committed. We extract once, into `packages/pikchr-corpus`, and commit every Script — `tests/`, `examples/`, `grammar/`, `fuzzcases/` and every `pikchr` fence under `doc/`.

The corpus is there to prove the grammar accepts everything upstream accepts, so breadth is the point and it can only grow when the pin moves. That is exactly when we want to *read* what changed, and a committed corpus makes a pin bump a reviewable diff rather than a test run that either passes or doesn't. Unpacking at test time tells us nothing on the runs that pass, hides the corpus from anyone reading the repo, and puts a `tar` subprocess and a 1.3 MB unpack in front of every `npm test`.

This is not a licensing question. Pikchr is Zero-Clause BSD, which grants copying and redistribution outright; ADR 0004's caution about pikchr covers its *documentation prose*, which is why hover documentation is written in our own words. A Pikchr Script inside a fence in `doc/userman.md` is Pikchr source, not that prose, and only fence bodies are extracted.

## Consequences

- One corpus, two consumers. `packages/pikchr-corpus` holds upstream Scripts and nothing else; the `.svg` goldens and `errors.txt` stay in `packages/pikchr-wasm/test/`, because those are output our own unpatched build produced, not upstream content, and they mean nothing to the grammar.
- Extraction is split from golden rendering, so refreshing the corpus needs no Emscripten — only regenerating the goldens does.
- Doc fences are named `<stem>-<short content hash>.pikchr`. `userman.md` alone holds 71 of the 157, and the corpus is regenerated by deleting and re-extracting, so ordinal names would turn a single inserted fence upstream into a 70-file rename. A content hash means a new fence adds one file and a name changes only when the Script did.
- **That naming decides the count, which is 261 and not 270** (amended during #1097). Content-addressing folds byte-identical fences together, and `userman.md` shows nine of its Scripts twice over — once as `pikchr source toggle indent`, once as `pikchr toggle indent` — which is one Script displayed two ways. Parsing it twice proves nothing, so the corpus holds it once; the folded names are listed under `duplicateFences` in the manifest, so the gap between 157 fences and 148 files is on the record rather than a discrepancy to rediscover. A clash between two *different* Scripts is a hash collision and stays fatal.
- The corpus records the check-in it came from, and a test asserts it matches `vendor/pikchr.lock.json` — the same guard `pin.test.ts` puts on the committed WASM, against the same mistake of bumping the lock and forgetting the rest.
- A pin bump that brings in a Script the grammar cannot parse fails the build. It is fixed, or recorded as a known gap with a reason; it is never recorded automatically, which would let the gap list fill itself and stop meaning anything.
- Upstream's deliberate error cases are asserted to *fail* to parse rather than excused from the corpus: they are the only negative cases we get for free. They are a separate list from `pikchr-wasm`'s `errors.txt` — four of its six render-error cases parse perfectly clean, because they are semantic errors, not syntax errors.
